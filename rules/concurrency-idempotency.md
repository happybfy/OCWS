# 并发与幂等巡检规范

本文档定义 OCWS 在**并发写入、中断重放、重复投递**场景下的幂等约束与一致性巡检规程，防止事实源被污染（重复任务行、重复变更条目、重复通知、重复派发）。

> 版本：`v1`（2026-10-10）
> 生效范围：OCWS 第一版
> 主执行者：计划者（Planner）在每次心跳/唤醒时执行 §4 巡检；其余机器人在自身动作中遵守 §2 幂等原则。

## 1. 背景与目的

第二小队为多机器人协作系统，`project.md` / `task.md` / 通知文件由多个机器人读写。当出现以下情况时，事实源可能出现重复或冲突：

- 计划者**并发运行**（同一次事件被两个运行各处理一次）；
- 运行**中断**后重放（记录已写、动作未执行，或动作已发生）；
- 事件/通知**重复投递**（同一 `event_id` / `notice_id` 多次到达）。

本规范给出：**幂等原则（§2）**、**写者约束（§3）**、**一致性巡检规程（§4）**、**收敛与升级（§5）**。

## 2. 幂等原则（全体适用）

1. **事件幂等**：同一 `event_id` 只处理一次；处理后事件文件 `inbox/ → cache/`，重复到达直接忽略（见 `push-notification.md`）。
2. **通知唯一**：同一 `project_id + task_id + attempt_id`，同一机器人至多存在一个**有效**通知（位于 `inbox/` 或 `working/`）。
3. **批次唯一**：同一任务同一时刻至多一个**有效授权**；重分配先撤销旧批次再签发新批次，`attempt_id` 递增（见 `task-lifecycle.md`）。
4. **事实源唯一**：`task.md` 是任务的唯一事实源；`project.md` 批次表中同一 `task_id` **只有一行**；变更记录中同一事件**只记一条**（以「时间戳 + 摘要」判重）。
5. **派发前查重**：生成通知前，必须检查目标机器人 `inbox/` 与 `working/` 是否已存在同键通知；已存在则不重复生成。
6. **不重放已发生动作**：中断恢复时，**记录已写但动作未执行** → 补做动作；**动作已发生** → 只补记录，不重跑（见 `task-lifecycle.md`「中断与人工恢复流程」）。

## 3. 写者约束

- 同一 workspace、同一时刻建议**只有一个计划者写者**写入 `project.md` / `task.md` / 通知文件。
- 检测到并发写入痕迹（重复行、重复条目、重复通知、同一任务多批次并行）→ 视为**流程异常**，按 §4 收敛。

## 4. 一致性巡检规程（计划者每次心跳/唤醒执行）

设 `P = 10-projects/<project_id>`、`R = 20-robots/<robot>`。

1. **收件箱巡检**：扫描自身 `inbox/`；按 `event_id` / `notice_id` 判重（已在 `cache/` 或已处理者跳过）；处理后将反馈类（`verify_result` / `alert` / `return` / `takeover_request`）移入 `cache/`。
2. **事实源核对**：
   - `project.md`：批次表内同一 `task_id` 无重复行；变更记录同一事件无重复条目；状态列与对应 `task.md` 一致。
   - `task.md`：`当前状态` 与「执行批次记录」一致；历史批次未被覆盖或改写。
3. **通知—状态一致性**：每条通知 `status` 与其所在子目录语义一致（`inbox`→`assigned` / `working`→`working` / `done`→`done` / `failed`→`failed`）；`task.md` 状态与通知位置不矛盾——**冲突以 `task.md` 为准**，并标记流程异常。
4. **授权唯一性**：每个机器人对每个 `task_id + attempt_id` 至多一个有效通知；同一任务至多一个有效批次。
5. **依赖纪律**：不为依赖未全部归档的任务生成通知（`task-lifecycle.md`）。
6. **异常处理**：
   - **重复行 / 重复条目** → 去重，保留**单一权威记录**（保留最早/最完整者）；
   - **记录已写、动作未执行** → 补做动作（幂等）；
   - **状态冲突** → 以 `task.md` 为准修正并记录；
   - **并发写者** → 收敛为单写者，重复产物按上述去重。
7. **记录**：巡检发现的异常与纠正动作写入 `20-robots/<planner>/logs/YYYY-MM-DD.md`（含时间、对象、异常、动作、依据）。

## 5. 收敛与升级

- 同一异常在短时间内**重复出现 ≥ 2 次** → 升级为结构性缺陷：以 `alert` 上报人类，并建议将入口收敛为**单计划者 / 单写者**。
- 不得为消除重复而删除历史批次、证据或通知；**只允许去重「重复」条目**，历史保留不变。

## 6. 禁止事项

- 禁止并发签发同一 `task_id + attempt_id` 的多个**有效**通知。
- 禁止用覆盖或删除历史批次的方式「修复」重复。
- 禁止在未核对既有状态的情况下重跑中断任务。

## 7. 与其它规则的关系

- `task-lifecycle.md`：状态流转与「中断与人工恢复流程」为本规范提供依据；
- `notice-schema.md` / `naming.md`：通知唯一性与命名唯一键（`project_id + task_id + attempt_id`）；
- `push-notification.md`：事件幂等（`event_id` 去重）与人类通知分级；
- `authorization-boundary.md`：证据分层与授权边界。
- `project-lock.md`：项目级串行（一队一项目）与切换硬门。
- `progress-patrol.md`：队长进度巡检与停滞升级。
