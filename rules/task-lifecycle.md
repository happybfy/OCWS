# 任务状态流转规范

本文档定义 OCWS 中任务从创建到归档的标准状态流转规则。目标是让项目目录、通知文件和机器人处理流程在状态表达上保持一致，避免“同一任务多种状态含义”的问题。

## 适用范围

本规范适用于：

- 项目目录中的 `task.md`
- 机器人目录中的通知文件
- 后续可能增加的结构化元数据文件

## 状态定义

第一版统一使用以下状态值：

### `new`

含义：

- 任务已创建
- 任务内容已具备最小执行信息
- 尚未正式分配给任何机器人

### `assigned`

含义：

- 任务已被分配给某个机器人
- 对应通知文件已生成或准备生成
- 尚未被机器人正式领取执行

### `working`

含义：

- 机器人已接收并开始执行
- 任务可能正在产生中间产物
- 当前不应再被其他机器人重复领取

### `done`

含义：

- 任务目标已完成
- 输出物已回写到任务目录的约定位置
- 任务已具备验收条件

### `failed`

含义：

- 任务执行失败，当前无法自动完成
- 需要人工介入、重新分配或补充输入信息

### `archived`

含义：

- 任务生命周期已关闭
- 不再继续修改
- 仅保留查询、审计和复盘用途

归档必须记录 `closure_reason`，用于区分关闭原因：

| `closure_reason` | 含义 | 谁决定 |
|------------------|------|--------|
| `verified` | 验收通过后正常关闭 | 门禁者判定，计划者执行 |
| `cancelled` | 人工决定取消（业务价值消失或范围变更） | 人工批准 |
| `terminated` | 失败终止（无法或不值得继续） | 人工批准 |

不得用 `verified` 伪装人工取消或失败终止，反之亦然。缺少 `closure_reason` 的归档视为流程异常。

## 标准流转路径

标准状态流转如下：

```text
new -> assigned -> working -> done -> archived
                       └------> failed

done -> assigned            （验收退回，产生新执行批次）
failed -> assigned          （补齐信息后重新分配）
failed -> archived          （确认终止）
```

说明如下：

- `new -> assigned`：任务完成准备并被正式分配
- `assigned -> working`：机器人领取任务并开始处理
- `working -> done`：任务完成且结果已回写
- `working -> failed`：处理中发现阻塞或错误，无法继续
- `done -> archived`：门禁者判定验收通过，计划者执行归档（`closure_reason: verified`）
- `done -> assigned`：门禁者判定验收退回（**不是** `failed`），计划者据此重新分配并开启新执行批次
- `failed -> assigned`：执行失败后补齐信息或修复阻塞，重新分配
- `failed -> archived`：确认终止，不再处理

> `done -> assigned` 与 `failed -> assigned` 的区别：前者是「已交付但验收不合格」，后者是「执行本身失败」。两者都必须保留前一批次的记录。

## 非法流转

以下流转默认视为非法：

- `new -> done`
- `new -> working`
- `assigned -> done`
- `done -> working`
- `archived -> working`
- `archived -> assigned`

如果确实需要例外处理，必须在任务说明中记录原因，并由人工确认。

> 验收退回**不得**使用 `done -> working`。退回不等于把任务拉回执行中，它必须走 `done -> assigned` 并新建批次，否则前一批次的交付与证据会被覆盖。

## 单一事实源

任务状态的单一事实源优先级如下：

1. 项目目录中的 `task.md`
2. 后续若引入结构化状态文件，则以结构化文件为准
3. 机器人通知文件中的状态仅作为流程视图，不作为最终事实源

这意味着：

- 任务最终状态必须回写到 `task.md`
- 机器人目录中的状态变化不能代替项目目录中的更新
- 如果项目目录与通知文件状态不一致，以项目目录为准，并视为流程异常
- `task.md` 只记录**当前有效结论**；历史批次的结论、产物与证据不得因重新执行而被覆盖或改写
- 各证据载体的权威顺序与冲突处理流程见 `rules/authorization-boundary.md`「证据分层」

## 各状态下的最小要求

### 当状态为 `new`

任务至少应具备：

- 任务标题
- 背景或上下文
- 目标
- 输入信息
- 验收标准

### 当状态为 `assigned`

除 `new` 的要求外，还应具备：

- 目标机器人
- 分配时间
- 通知文件位置

### 当状态为 `working`

除 `assigned` 的要求外，还应具备：

- 开始执行时间
- 当前执行者
- 执行中备注或中间记录入口

### 当状态为 `done`

除 `working` 的要求外，还应具备：

- 完成时间
- 输出位置
- 完成摘要

### 当状态为 `failed`

除 `working` 的要求外，还应具备：

- 失败时间
- 失败原因
- 是否可重试
- 建议下一步

## 目录动作建议

状态变化应尽量与目录动作保持一致：

- `assigned`：通知文件进入目标机器人 `inbox/`
- `working`：通知文件移动到 `working/`
- `done`：通知文件移动到 `done/`
- `failed`：通知文件移动到 `failed/`

注意：

- 目录动作是工作流表现，不是最终事实源
- 无论通知文件移动到哪里，项目目录中的 `task.md` 都必须同步更新

## 执行批次（attempt_id）

每次实际执行分配一个 `attempt_id`（从 `a1` 起递增）。要求：

- 同一任务同一时刻**最多只有一个有效执行授权**；重分配时必须显式撤销旧授权。
- 批次记录至少包含：执行者、起止时间、结果、证据路径。
- 批次文件按 `logs/att-a{N}/`、`output/att-a{N}/` 组织，**不得覆盖**旧批次。
- 重试、退回重交、接管都创建新批次，并保留旧批次作为审计证据。

## 失败与重试规则

对于 `failed` 状态，遵循以下规则（本节为**强制**要求）：

- 必须先记录失败原因，再决定是否重试
- 同一失败原因不应无限重复重试
- 重新分配前，必须先补齐缺失输入或修复阻塞条件
- 如任务已失去业务价值，可转为 `archived`（`closure_reason: terminated`），需人工批准
- 重试必须新建执行批次并写入 `attempt_id`，不得覆盖上一批次记录

### 超时与接管（强制）

超时只能证明「需要检查」，**不能证明执行者已经停止**。因此：

1. 超时后只允许**告警**，由门禁者/计划者通知管理者，不得自动接管。
2. 接管前必须确认原执行者及其相关外部操作已停止或结束。
3. 必须检查已有产物和外部操作的**实际结果**。
4. 由管理者批准恢复方式，再由计划者重新分配（`task.reassigned`）。
5. 无法确认原执行者已停止时，任务保持暂停，**不得并行启动替代执行**。

告警阈值按任务预计时长配置；现有「working/ 超 2 小时告警、超 4 小时申请接管」仅作默认参考，不作为通用故障判定依据。本版**不引入**租约、自动接管和授权版本隔离机制。

## 中断与人工恢复流程

通知移动、通知内容更新与 `task.md` 更新不是一个整体事务。中途退出会产生不一致，不能只靠「以 task.md 为准」处理，必须走以下人工恢复流程：

1. 暂停受影响任务，禁止自动再次执行。
2. 核对 `task.md`、通知位置、批次执行记录、产物和外部操作结果。
3. 判断属于以下哪一种：记录漏写 / 尚未执行 / 执行失败 / 结果仍不确定。
4. 记录判断依据、处理人和恢复动作（写入 `logs/recovery-{日期}.md`）。
5. 按判断结果处理：
   - 已完成的操作 → 只补写记录，**不重复执行**；
   - 确需重试 → 创建新批次，保留旧批次；
   - 结果不确定 → 保持暂停并继续核验。

常规写入也应约定角色交接顺序，避免计划者、执行者和门禁者同时整篇修改 `task.md`。验收标准发生变更时，必须留痕并明确它适用于哪个批次。

## 人工介入要求

以下情况**必须**获得人工批准并留痕（记录批准人与原因）：

- 任务从 `failed` 重新转为 `assigned`
- 任务被判定为 `done` 但缺少明确交付物
- 任务需要跳过某些标准状态
- 任务准备直接终止并归档（`closure_reason: cancelled` / `terminated`）
- 超时后启动接管执行（见「超时与接管」）
- 高影响 / 不可逆操作执行前（见 `rules/authorization-boundary.md`）

本规范不使用「建议必须」这类双重措辞：每条要求要么是强制，要么是可选，必须写明。

## 归档责任

归档只允许一种模式：

- **门禁者**负责依据验收标准给出通过 / 退回结论，并保存验收报告。
- **计划者**负责依据该结论提交归档（`done -> archived`，写入 `closure_reason`），**不得绕过验收失败结论归档**。
- 人工终止任务需记录批准人与原因，`closure_reason` 用 `cancelled` / `terminated`，不伪装成验收通过。

门禁者不得自行把任务标记为 `archived`，也不得直接移动项目 `archive/` 下的内容。
