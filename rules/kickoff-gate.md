# 立项评审门（Kickoff Gate）

本文档定义**新项目开工前**的强制确认门：**先讨论确认，再落实到具体文档，然后才允许开工**。

> 目的：避免「范围未定就开发」「边做边改范围」「无人类确认即派工」。门在**项目启动前**，不在任务执行中。

## 1. 适用与触发

- **触发**：任何**新项目**（`10-projects/` 下新建 `PRJ-*`）在**派发第一个开发任务之前**。
- **不适用**：既有项目内新增任务（走 `task-lifecycle.md`）；纯运维/一次性操作。

## 2. 流程（硬门）

```text
讨论（人类 + 主管 + 本队队长/计划者）
   → 确认（人类签字）
   → 落文档（最小集，见 §3）
   → 放行（才允许创建 T02+ 开发任务并派发）
```

**硬门**：**无「人类确认记录」或 `access-matrix.md` 未签核 = 不得派发任何开发任务**（只能停在立项/拆解阶段，机器人不得开工）。

## 3. 落文档最小集

| 文档 | 内容 | 位置建议 |
|------|------|---------|
| `scope.md` | 范围边界、本期/非本期、验收标准 | 项目 `docs/` 或 `shared/refs/` |
| `adr.md` | 关键架构决策（ADR 集） | 同上 |
| `external-dependencies.md` | 外部依赖与负责人 | 同上 |
| `test-plan.md` | 初版验收表（门禁 G0–G3 口径） | 同上 |
| `approval-record.md` | **人类确认记录（签字 + 时间）** | 同上 |
| `access-matrix.md` | **访问与权限矩阵（账号、级别、边界、有效期、回滚）** | 同上 |

> 文档路径可按项目约定调整，但**六类内容缺一不可**；`approval-record.md` 与 `access-matrix.md` 是放行的凭据。

### 3.1 `access-matrix.md` 必填项（硬门）

| 项目 | 内容 |
|---|---|
| 账号/凭据 | GitLab、NFS、bdpan A/B、生产 DB/API、ESXi/云；持有者、有效期 |
| 访问级别 | 只读 / 测试写 / 生产写，逐项标明 |
| 操作边界 | 团队可自行执行的操作；必须人类批准的操作（生产写、删除、对外分享、改凭据） |
| 凭据存放 | SecretRef / 受控引用；禁止明文写入通知与普通日志 |
| 回滚能力 | 备份位置、回滚方式、责任人 |
| 签核 | Sponsor 签字 + 时间；计划者核验记录 |

未签核或字段缺失的 `access-matrix.md` 视为未通过立项门。

## 4. 责任

| 角色 | 动作 |
|------|------|
| Sponsor（人类负责人） | 参与讨论、**签字确认**、**签核访问矩阵** |
| 主管 / 队长 | 组织讨论、核验六类文档齐备、放行 |
| 计划者 | 核验 `access-matrix.md` 与五类文档后才创建并派发 T02+ 开发任务 |

## 5. 例外

- 如确需**先开**（如总范围已由上游文档冻结），**必须在 `task.md` 显式留痕**并说明「先开依据」，且**仍须在最短时间内补齐人类确认**。
- 例外不得由机器人单方面决定；留痕须可追溯（时间、依据、确认人）。
- 未留痕的「先开」视为**违规开工**，门禁者/计划者应上报人类。

## 6. 与门禁（Gate）的关系

- **Kickoff Gate（本文档）**：项目**启动前**的门（G0 前置），保证"先定后做"。
- **G0–G4（`SPEC.md` §8 / 项目分解）**：项目**进行中**的里程碑门。
- 关系：Kickoff Gate 通过 → 允许创建开发任务；G0 冻结范围 → 允许进入施工。二者不可互相替代。
