## 1. 动机

**现象**：多小队并行时，人类与主管（砂糖橘）共用**同一个会话**承载三队上下文 → 信息串味、上下文膨胀、易混乱。

**定性**：不是"层级不够"，而是**上下文边界缺失**。解法 = 给每小队一个**独立会话边界 + 对外接口（队长）**。

---

## 2. 组织结构

```text
不舟子（人类）
  └─ 主管 / Supervisor（砂糖橘 · main 本机）
       ├─ 队长 · TEAM-1（不舟AI）      ─┐
       ├─ 队长 · TEAM-2（新组建）      ─┤ 每队：计划者 → 执行者 / 门禁者
       └─ 队长 · TEAM-4（途安车联）    ─┘
```

- **人类 ↔ 主管**：单队运行时的直连通道。
- **人类 ↔ 队长**：多队并行时，人类按队与队长沟通，避免跨队上下文混入。
- **主管**：跨队总进度、跨队资源仲裁、全局门禁（G0–G4）。

---

## 3. 角色定义（Captain · 队长）— **本队范围的主管**

### 3.1 定位（rev2 修正）

队长 = **本队范围内的"主管"**：与主管**职责同构**（统筹、协调、汇报、边界内仲裁），只是**作用域限于本队**（本队项目/任务/资源），且**无跨队仲裁权、无全局门禁权**。

> 一句话：**队长是本队的"小主管"（mini-me），不是只读看板。** 人类对主管的用法（问进展、要统筹、拍方向），对队长同样适用，只是边界收在本队内。

### 3.2 职责（与主管同构，范围=本队）

| # | 职责 | 说明 |
|---|------|------|
| 1 | **本队统筹** | 统筹本队项目/任务进度与优先级；在**本队资源边界内**做调度决策 |
| 2 | **管理信息输出** | 向人类输出本队的管理信息（进展/风险/里程碑/建议）——这就是"避免上下文混在一起"的载体 |
| 3 | **向计划者下需求** | 以 `REQ-TEAM-<n>-*` 向**计划者** inbox 投递（新增任务/调整范围/重开批次） |
| 4 | **对外汇报** | 以 `REPORT-TEAM-<n>-*` 向**主管/人类**汇报本队情况 |
| 5 | **边界内仲裁** | 本队资源/依赖/优先级冲突，在**本队权限内**裁决；超出边界→升级 |
| 6 | **阻塞与升级** | 本队阻塞按升级路径上报（跨队/高影响 → 主管 → 人类） |

### 3.3 与主管的异同

| 维度 | 主管 | 队长 |
|------|------|------|
| 作用层 | 在**计划者之上**（编排层） | 同（在**本队计划者之上**） |
| 统筹/汇报/协调 | ✅ 全局 | ✅ 本队 |
| 资源仲裁 | ✅ 跨队 | ✅ 仅本队边界内 |
| 全局门禁 G0–G4 | ✅ | ❌（本队门禁参与，不持全局放行权） |
| 直连人类 | ✅（单队模式） | ✅（多队模式·本队） |
| 写 `task.md` | ❌（经计划者） | ❌（经本队计划者） |

> **关键不变式**：队长与主管**都不写 `task.md`/`project.md`** —— 事实源唯一写者是**计划者**。队长通过对计划者下 REQ 来施加意志，与主管对我的做法一致。

### 3.4 不越界（硬约束）

| ❌ 禁止 | 因为 |
|---------|------|
| 写 `project.md` / `task.md` | **计划者是事实源唯一写者** |
| 生成/投递 `NOTICE-*`（派工） | 派工 = 计划者 |
| 验收 `done/`、出归档/退回结论 | = 门禁者 |
| 执行具体任务、改产出 | = 执行者 |
| 越过本队边界调度他队资源 | = 主管 |
| 持有全局门禁放行权 | = 主管 |

> 队长可写：`REQ-TEAM-<n>-*`（给计划者）、`REPORT-TEAM-<n>-*`（给主管/人类）、升级上报。

## 4. 写权限边界（防双头）

| 对象 | 唯一写者 | 队长可见 | 队长可写 |
|------|---------|---------|---------|
| `project.md` / `task.md` | 计划者 | ✅ 读 | ❌ |
| `NOTICE-*`（派工） | 计划者 | ✅ 读 | ❌ |
| `EVENT-*`（流程事件） | 执行者 / 门禁者 | ✅ 读 | ❌ |
| `output/` / `logs/` | 执行者 | ✅ 读 | ❌ |
| `REQ-TEAM-<n>-*` | **队长** | ✅ | ✅ → 计划者 `inbox/` |
| `REPORT-TEAM-<n>-*` | **队长** | ✅ | ✅ → 主管/人类 |
| 升级/阻塞上报 | **队长** | ✅ | ✅ |

## 5. 汇报文件规范

### 5.1 命名

```text
REPORT-TEAM-<n>-<YYYYMMDD-HHmm>.md      # 例行/事件汇报
REQ-TEAM-<n>-<short>.md                  # 向计划者下需求
```

`<n>` ∈ {1, 2, 4}。

### 5.2 最小字段

- `report_id` / `team_id`
- `period`（统计窗口）
- `projects[]`：项目、当前批次、门禁、健康度
- `tasks[]`：任务、状态、执行者、批次、证据指针
- `risks[]`：风险/阻塞、影响、需要的决策
- `next[]`：下一步计划与依赖
- `created_at` / `status`

> 原则同 OCWS：**只给指针，不复制正文**。

## 6. 升级路径（Escalation）

```text
执行者/门禁者（队内）
   ↓ 队内问题
计划者（事实源）
   ↓ 需对外/需本队决策
队长（本队主管）
   ↓ 跨队 / 全局 / 超边界
主管
   ↓ 需人类拍板
人类（不舟子）
```

- 队内常规问题**队内闭环**，不上升。
- 仅**跨队冲突 / 超边界 / 需人类决策**才上升。
- 高影响/不可逆操作仍按 `authorization-boundary.md`：**执行前显式授权 + 留痕**。

## 7. 单队 / 多队 切换规则（硬规则）

| 场景 | 人类找谁 | 理由 |
|------|---------|------|
| **仅一队在跑** | 直接找**主管** | 无跨队混淆，链路最短 |
| **多队并行 · 单队任务详情** | 找**该队队长** | 上下文隔离 |
| **跨队 / 全局 / 总进度** | 找**主管** | 跨队资源与全局门禁只有主管可见 |

> 判据：**跨队共用资源、全局门禁、总进度 → 主管；单队内部任务详情 → 该队队长。**

## 11. 立项评审门（Kickoff Gate）★ 本次新增

> 对应不舟要求：**项目在启动前，先讨论确认，并落实到具体文档**。

### 11.1 规则

**任何新项目，开工前必须过「立项评审门」：**

```text
讨论（人类 + 主管 + 本队队长/计划者）
   → 确认（人类签字）
   → 落文档（scope.md / adr / 外部依赖表 / 初版验收表）
   → 放行（才允许建 T02+ 开发任务）
```

**硬门**：无「人类确认记录」= **不得派发任何开发任务**（只能停在立项/拆解阶段）。

### 11.2 落文档物（最小集）

| 文档 | 内容 |
|------|------|
| `scope.md` | 范围边界、本期/非本期、验收标准 |
| `adr.md` | 关键架构决策（ADR 集） |
| `external-dependencies.md` | 外部依赖与负责人 |
| `test-plan.md` | 初版验收表（G0–G3 口径） |
| `approval-record.md` | **人类确认记录（签字 + 时间）** |

### 11.3 现实缺口（rev2 核查结论）

- ✅ **云笈（PRJ-002）实际做到了**：T01 产出上述五件 + 不舟签字（`2026-10-09T22:59:47+08:00`），G0 放行。
- ⚠️ **但这是"项目级一次性做法"**：写在云笈的任务分解文档里，**规则层 `00-system/rules/` 没有通用门**。
- ⚠️ **且云笈自己开了例外**：T02/T03 以「T01 范围已由《完整实施方案》冻结」为先开依据 → 先于签字开工 → **门是软的**。

→ 结论：**该机制目前不是系统默认强制的**。本规则把它固化为**通用 Kickoff Gate**，所有新项目默认适用；如需例外，必须在 `task.md` 显式留痕并由人类确认。

## 14. 风险与反模式

| 风险 | 后果 | 防护 |
|------|------|------|
| 队长写 `task.md` | 与计划者双写者冲突 | §3.4 硬禁止 + §4 权限表 |
| 队长成为派工一跳 | 每任务多延迟 | 队长不派工，只下 REQ |
| 队长权限越界到他队 | 跨队冲突、主管失效 | §3.3/§8 边界 |
| 切换规则不清 | 反复纠结找谁 | §7 硬规则 |
| 立项评审门形同虚设 | "先开依据"绕过签字 | §11.3：例外须留痕 + 人类确认 |
| 跨队资源冲突被漏看 | 两队同宿主争用致故障 | §8 纳入主管视图 |
